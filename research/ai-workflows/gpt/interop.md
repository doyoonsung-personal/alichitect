**Research date: 2026-11-02.** Read-only research; no files created or changed. “Unconfirmed” means the reviewed documentation does not establish the claim—not that the capability is necessarily absent.

The catalog should distinguish six connection types: **model inference, tool access, agent delegation, frontend events, skill loading, and telemetry**. A single “agent-compatible” flag would hide material differences.

**1. MCP: current specification and interoperability**

| Topic | Confirmed finding | Implication for the app |
|---|---|---|
| Current version | The official `latest` specification resolves to **2026-07-28**. [MCP specification](https://modelcontextprotocol.io/specification/2026-07-28) | Store the actual supported revision on each integration. |
| Major compatibility change | This revision removes the `initialize`/`initialized` exchange and `Mcp-Session-Id` header from the new protocol core. It introduces stateless operation, multi-round-trip requests and updated routing metadata. [Release explanation](https://blog.modelcontextprotocol.io/posts/2026-07-28/) | Do not assume an implementation documented around initialization/session affinity supports the latest revision. |
| `stdio` | Standard transport using newline-delimited messages over a client-launched subprocess’s standard streams. [Transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) | Draw inside the runtime/process boundary; it is not a remote network endpoint. |
| Streamable HTTP | Standard remote transport: individual HTTP POSTs to one MCP endpoint; responses can be JSON or request-scoped SSE streams. Messages use JSON-RPC. [Transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) | Label the edge `MCP / Streamable HTTP`, not merely `SSE`. |
| Older implementations | Earlier revisions use a connection-scoped initialization handshake; the current specification explicitly describes backward compatibility. [Transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) | Keep legacy HTTP+SSE and current Streamable HTTP as separate capability values. |
| Remote servers | Remote servers expose an HTTP endpoint; current Streamable HTTP supports JSON responses and streaming responses on that endpoint. [HTTP binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) | Record URL, network reachability, authentication and transport separately. |
| Authorization | Authorization is optional at the protocol level. HTTP implementations supporting authorization should follow the MCP authorization specification; stdio implementations should obtain credentials from the environment instead. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) | “Supports MCP” does not establish production authentication. |
| OAuth roles | A protected MCP server is an OAuth resource server; the MCP client is an OAuth client. Authorization servers issue access tokens. The specification uses OAuth 2.1, protected-resource metadata and resource indicators. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) | Represent client→MCP authorization separately from MCP→downstream-service credentials. |
| Client registration | Client ID Metadata Documents are recommended; Dynamic Client Registration is deprecated but retained for backward compatibility. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) | Avoid making dynamic registration mandatory for every OAuth integration. |
| Official registry | The official MCP Registry remains **preview**. It publishes `server.json` metadata, package locations, remote URLs and installation information through a REST API. It stores metadata rather than hosting server binaries. [Registry documentation](https://modelcontextprotocol.io/registry/about) | Registry discovery should populate candidate integrations, not automatically enable them. |
| Private registries | The public registry excludes private-network/private-package servers and recommends a separate private registry for them. Downstream aggregators can add curation. [Registry documentation](https://modelcontextprotocol.io/registry/about) | Support an enterprise-approved registry independent of public discovery. |

**Governance and adoption.** Anthropic donated MCP to the **Agentic AI Foundation (AAIF), under the Linux Foundation**, in December 2025. Its announcement identifies adoption by ChatGPT, Gemini, Microsoft Copilot, VS Code and Cursor, plus deployment support from AWS, Google Cloud and Azure. These are adoption statements, not guarantees that every product implements every revision. [Anthropic announcement](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)

OpenAI’s Responses API explicitly supports remote MCP servers and exposes tool approvals; this is concrete API-level adoption. [Official OpenAI documentation](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)

**2. A2A: version, governance and adoption**

| Topic | Confirmed finding | Diagram/catalog treatment |
|---|---|---|
| Purpose | Agent2Agent standardizes communication between independent, potentially opaque agents, allowing cooperation without exposing their internal tools or memory. [Project overview](https://a2a-protocol.org/latest/) | Use for delegation to an independently executing agent. |
| Current release | The official release repository marks **v1.0.1** as latest; its changelog date is 2026-05-26 and GitHub release date is May 28. [Official releases](https://github.com/a2aproject/A2A/releases) | Pin `1.0.1`; do not confuse SDK version numbers with protocol releases. |
| Discovery and execution | The specification defines Agent Cards, messages, tasks, artifacts, streaming/asynchronous interaction, and JSON-RPC, gRPC and HTTP/REST bindings. [A2A specification](https://a2a-protocol.org/latest/specification/) | Record Agent Card URL, binding, task lifecycle and streaming capability. |
| Governance | A2A joined AAIF as a **Growth Stage project**, announced August 27, 2026. “Linux Foundation project” remains broadly accurate, but AAIF is the more precise current home. [Project announcement](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/) | Record governance separately from Google’s role as originator. |
| Adoption | The Linux Foundation reported more than 150 supporting organizations and integrations across Google, Microsoft and AWS in April 2026. [Foundation announcement](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year) | Distinguish ecosystem participation from a tested product integration. |

**Recommended distinction:** a “search help centre” operation is normally a tool edge; “delegate resolution to the independently deployed billing agent” is an agent edge. Do not label every connection between workflow steps A2A.

**5. Production MCP security**

| Risk | Evidence and required treatment |
|---|---|
| **Tool poisoning / prompt injection** | Tool descriptions can contain instructions that hijack agent behaviour; tool changes can create “rug pulls,” and cross-server interactions can enable tool shadowing. Invariant documents scanning, tool-definition hashing and runtime controls. **Recommendation:** approve servers and tool definitions, detect changes, and treat tool results as untrusted data. [Invariant security documentation](https://invariantlabs-ai.github.io/docs/mcp-scan/) |
| **Over-permissioned servers** | MCP security guidance calls for scope minimization; broad access increases the consequences of compromised clients or malicious content. **Recommendation:** separate read, draft and send tools; restrict downstream identities as well as visible tool names. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| **Token passthrough / confused deputy** | MCP guidance prohibits token passthrough and addresses proxy consent vulnerabilities. **Recommendation:** validate token audience and obtain separate downstream authorization; do not forward an inbound bearer token indiscriminately. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| **Authentication and discovery** | Implement protected-resource discovery, OAuth issuer validation and the applicable OAuth security controls. A gateway API key should not be advertised as implementing the complete MCP OAuth profile. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) |
| **DNS rebinding / exposed local servers** | Streamable HTTP requires Origin validation and rejection of invalid Origins; local servers should bind to localhost, with appropriate authentication. [HTTP security requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) |
| **SSRF / malicious discovery URLs** | MCP guidance covers SSRF against server/discovery infrastructure and authorization servers. **Recommendation:** restrict egress, validate destinations and redirects, and block unintended private/metadata addresses. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| **Local executable compromise** | Local MCP servers execute code; MCP guidance addresses sandboxing and local-server compromise. **Recommendation:** pin reviewed packages and isolate their filesystem, network and secrets access. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| **Cloud credential exposure** | Alibaba warns against account-level AccessKeys, hardcoded secrets and excessive RAM permissions, and recommends rotation. [OpenAPI MCP security guidance](https://www.alibabacloud.com/help/en/openapi/user-guide/openapi-mcp-server-guide) |
| **Sensitive actions** | OpenAI’s MCP integration supports explicit approval controls and stresses trusting remote servers. **Recommendation:** enforce approvals in application/backend policy, with action arguments visible to the reviewer. [Official OpenAI MCP guidance](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) |

**6. Recommended catalog fields, drawing rules and tests**

These are implementation recommendations derived from the distinctions above.

| Area | Concrete rule |
|---|---|
| Capability record | Store `protocol`, `revision`, `transport`, `role`—consumer/server/proxy/adapter—`endpoint`, `region`, `account_eligibility`, `auth_profile`, `source_url`, `verified_at`, and `evidence_status`. |
| Protocol compatibility | Store `unknown` rather than assuming the latest revision. Match transport and revision separately. An SSE endpoint is not automatically compatible with a Streamable HTTP-only client. |
| Diagram edges | Use explicit labels: `model inference`, `MCP tool call`, `A2A delegation`, `AG-UI events`, `skill load`, `OTel export`. Keep business branches, loops and approvals as workflow constructs. |
| Model ownership | Attach a model to the agent or inference step that calls it. A remote opaque A2A agent’s internal model should be `unknown` unless declared. |
| Regional controls | Validate runtime, model, tool endpoint and telemetry destination independently. A Singapore runtime must not silently imply Singapore-only processing or storage everywhere. |
| Cost calculation | Count model calls, tool/API charges, runtime execution, gateway and telemetry separately. Do not hardcode FC’s older two-request initialization example into every MCP tool call. |
| Live updates | Maintain stable workflow/node/run identifiers and correlate them with streamed events and trace/span IDs. A tool-argument event must not mark execution successful. |
| Security | Enforce permissions and approval gates outside model instructions; store credential references, not secrets, in diagram metadata or proposal exports. |

Minimum regression cases:

1. **New Singapore account:** reject legacy Model Studio application/knowledge-base selection while permitting supported model APIs.
2. **Transport mismatch:** reject an SSE-only Model Studio integration targeting a Streamable HTTP-only server.
3. **Revision mismatch:** distinguish MCP 2026-07-28 stateless operation from older initialization/session behaviour.
4. **Agent delegation:** validate Agent Card, binding, authentication and task completion before marking an A2A step successful.
5. **Poisoned email/tool result:** malicious instructions cannot obtain broader tools or bypass the send policy.
6. **Changed tool definition:** require re-review after an approved server changes a tool’s schema or description.
7. **Approval resume:** send exactly once after approval; never interpret reconnect, retry or argument-stream completion as approval.
8. **Telemetry duplication:** one model invocation produces one billable usage record despite overlapping instrumentation.
9. **Regional conflict:** AgentRun Hong Kong remains unconfirmed; AgentLoop’s Hong Kong destination is displayed separately from a Singapore workflow.
10. **Opaque agent:** a proposal never invents the remote agent’s model, token usage or internal topology.
